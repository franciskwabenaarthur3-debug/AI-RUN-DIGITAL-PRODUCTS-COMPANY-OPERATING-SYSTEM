# Security

This describes controls that are implemented now. Planned controls are listed separately so nothing is mistaken for done.

## Implemented

- **Accounts:** no public registration. Users are created with `php artisan company-os:create-user`, which requires a 12+ character password and records an audit event. `role` and `is_active` are not mass assignable.
- **Two-step sign-in:** time-based codes from an authenticator app (RFC 6238, implemented in `App\Security\Totp` and checked against the RFC test values), set up on the Account security page by scanning a QR code. The secret is stored encrypted with `APP_KEY` and never shown after setup; each code works once (the last accepted time step is stored) and one step of clock drift is allowed. Eight single-use recovery codes are shown once and stored only as SHA-256 hashes. After a correct password the session holds only a pending sign-in for 5 minutes; five wrong codes drop it, and a deactivated account cannot finish. Founders must use it (`SECURITY_REQUIRE_FOUNDER_TWO_FACTOR`, on by default): until it is set up they can reach only the Account security page, and they cannot turn it off. A lost phone without recovery codes is reset only from the server console (`company-os:reset-two-factor`), audited. Others can turn it off with their password and a code.
- **Passwords:** people change their own password with the current one; this clears "keep me signed in" tokens.
- **Browser headers:** every response sends a content security policy (scripts only from this site, no inline scripts or event handlers, no plugins, no framing, forms only to this site), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, a strict referrer policy, a permissions policy, and HSTS on HTTPS. Inline style attributes are allowed because the proposal document shares markup with the email. A test fails if any view adds an inline script.
- **Login:** Laravel session guard, bcrypt hashing, session regeneration on login, session invalidation and CSRF token rotation on logout. Logout is POST only.
- **Brute force:** 5 failed attempts per email + IP locks that pair out for 60 seconds (`LOGIN_MAX_ATTEMPTS`), plus a route throttle of 20 requests/minute per IP.
- **Deactivation:** inactive users cannot log in; an already logged-in user who is deactivated is logged out on the next request.
- **Authorization:** policies checked server-side in Form Requests and controllers, so direct requests cannot bypass hidden UI. Only founders can change settings or view the audit log.
- **CRM access:** founders and operators create and change leads and customers; viewers are read-only. Only founders manage service packages and see or change customer billing details. Every rule is checked in policies, and tests send direct requests to prove hidden controls cannot be bypassed.
- **Customer billing details:** encrypted at rest with `APP_KEY`, excluded from serialization and from audit metadata (audit records note only that billing changed). Rotating `APP_KEY` requires re-encrypting this column.
- **Mass assignment:** lead status, opt-out and conversion fields, and customer billing details are not fillable; they change only through services.
- **Opt-out:** an opted-out lead is flagged `do_not_contact`, cannot enter outreach states, and its email/domain cannot be re-entered as a new lead because of the unique constraints.
- **Search:** user search terms are bound parameters with LIKE wildcards escaped.
- **Agents:** see [agent policies](agent-policies.md). Agents start disabled; only founders enable them or change tool permissions; tools come from a fixed catalog; step, token, timeout, retry and budget limits are enforced by the runner, not by instructions; output is schema-validated and never treated as proof of an external action; the mock runtime is off outside local/testing.
- **Tool gateway:** agents act only through registered tools checked for prohibition, permission, agent status, pause, per-run call cap and input schema. Level 3 actions are refused outright. Tool input is never run as shell or SQL. Input and result summaries are redacted before storage.
- **Approvals:** only an active founder can decide (checked in `ApprovalService`, not just the policy). The approved payload is hashed; execution refuses missing, pending, rejected, expired, invalidated, already executed or in-progress approvals, and invalidates the approval if the payload about to run differs from the approved one or the stored snapshot was edited. A claim moves the request to `executing` under a row lock before the side effect runs, outside any transaction, so two workers cannot both execute it. A crash mid-execution is flagged `needs_reconciliation`, never silently retried. Agents have no route or tool to approve anything.
- **Proposals:** prices are computed in code from the package and entered lines; agents cannot supply prices, discounts or recipients. A version's content and lines are frozen once submitted (model guards). Sending needs the founder's approval of a payload hash covering the exact recipient, content and totals; the payload is recomputed from the database at send time and any difference invalidates the approval, so a changed proposal cannot reuse an approval. The approval claim makes a send happen at most once; a crash mid-send is flagged for reconciliation, never retried. Email is off by default, and a local `log`/`array` mailer is never reported as a delivery. Recipient opt-out is checked again right before sending.
- **Projects and releases:** a project is created once per accepted proposal (row lock plus a unique column). Production releases need every mandatory check passed with evidence, a verified staging release of the same version, the client's recorded approval and the founder's approval of a payload hash covering the version, URL, rollback plan and every check result; the release and its checks are frozen once submitted. Recording the deployment is founder-only, re-checks every gate (an approval cannot override a failed mandatory check) and goes through the approval claim, so it happens once and any change invalidates the approval. Company OS never deploys, runs build commands or uses deployment credentials; agents have no release tools. The health check is the only outbound request: http(s) only, no credentials in the URL, every resolved address must be public (private, loopback, link-local and reserved ranges refused, so cloud metadata addresses cannot be reached), the connection is pinned to the checked address, redirects are reported and not followed, and it has a timeout (`RELEASE_HEALTH_CHECK_TIMEOUT`). `RELEASE_HEALTH_CHECK_ALLOW_PRIVATE` turns the address check off for local testing only. Project and deliverable links must be http(s) and cannot contain a user name or password.
- **Maintenance and reports:** plans and prices are founder-only. Visit checklists hold non-destructive checks, and the only request Company OS makes is the same guarded health check as releases. A change to a live site needs the founder's approval of a payload hash covering the site, the finding, the change plan and the rollback plan; recording the change goes through the approval claim, so it is recorded once and any edit afterwards invalidates the approval. A risky finding cannot be closed as resolved without it. Completed, failed and cancelled visits and their findings are frozen (model guards); stored reports cannot change or be deleted. Reports and cost pages need operator or founder access. Alerts are in-app only. Agents can schedule visits and read reports, nothing else.
- **Audit:** append-only `audit_logs` (model guard + PostgreSQL trigger). Failed logins store a SHA-256 hash of the attempted email, not the email or password. Keys matching `config('company_os.redacted_keys')` are replaced with `[redacted]` at any nesting depth.
- **Tracing:** every response carries an `X-Request-Id` (a valid incoming UUID is reused, anything else replaced). It is stored on audit records.
- **Sessions:** stored in the database and encrypted (`SESSION_ENCRYPT=true`). Set `SESSION_SECURE_COOKIE=true` on HTTPS environments.
- **Files:** the local disk's signed-URL serving route is disabled (`serve => false`).
- **AI provider:** the API key is read from `ANTHROPIC_API_KEY` only, never stored in the database or logs; provider error messages are shortened and authentication errors never include provider text. Task content, tool results and web content are marked as untrusted data in prompts, but no control depends on that: the model cannot change permissions, approve anything or exceed limits, because those are enforced in code. Model output is accepted only through the `submit_result` tool and validated against the output schema; tool calls are validated by the gateway. Lead email addresses and phone numbers are not sent to the provider. No sending tool exists.
- **Backups:** made with `pg_dump`/`pg_restore` called with fixed arguments (no shell), the password passed in the environment, files written `0600` to a private folder with a SHA-256 checksum. Restore tests refuse the live database as a target and refuse a file whose checksum changed. Backups contain encrypted columns, so `APP_KEY` must be kept with them (and kept separately from them).
- **Secrets:** none in source; `.env` is git-ignored and `.env.example` holds keys only.

## Not implemented

- A customer portal: clients have no logins, so "one customer cannot see another's records" is tested for staff roles, guests, deactivated accounts and nested URLs (acceptance case 4). Repeat it for client logins if a portal is built.
- Database-level immutability trigger for approval decisions (today: model guard plus the unique constraint).
- SSRF protection for agent website-reading tools (with the first such tool; the release and maintenance health check has its own guard).
- File uploads (there are none, so no upload validation yet) and automatic data retention or deletion; see the retention notes in [backup and recovery](backup-recovery.md).
- Email delivery of alerts; alerts are in-app.
